# 足球预测系统优化路线图

## 1. 文档目的

本文档定义项目下一阶段的优化顺序、工程边界、验收标准和交付方式。核心原则是先保证结果可复现、模型状态真实、回测可信，再讨论增加模型、优化页面或部署扩展。

本文档不是功能愿望清单。每个阶段都设置退出条件，未达到退出条件时，不进入依赖该阶段结果的后续工作。

## 2. 当前状态

项目已经具备以下能力：

- Flask Web 页面和 JSON API。
- 泊松、Dixon-Coles、ELO、Massey、近期状态、交锋、市场赔率、KNN、XGBoost、神经网络、蒙特卡洛和贝叶斯模型接口。
- BMA 融合、校准脚本、历史数据抓取和本地缓存。
- 竞彩足球分析与方案规划。
- 独立的彩票历史统计模块。

迭代 A 已解决：

- ELO 初始化已改为按数据指纹加载或确定性重建，重复启动不会重复累计。
- `knn` 旧权重会迁移到规范键 `knn_similar`。
- 未训练、特征不兼容或概率非法的模型不会进入融合。
- “置信度”已改为“模型一致度”，旧字段暂时保留兼容。
- 已建立默认断网的项目级自动化测试。

迭代 B 的 PR 1 已解决：

- 无真实赔率时市场模型退出融合。
- 蒙特卡洛改为最终融合结果的派生采样，实际权重固定为 0。
- Massey 概率裁剪后重新归一化。
- 历史抓取日期改为动态最近 14 个完整自然日。
- 数据刷新、FIFA 同步、校准和彩票强制刷新改为受管理令牌保护的 POST。
- 已建立 Python 3.10 和 3.12 的持续集成门禁。

当前主要限制：

- 当前校准中的部分模型使用固定先验或占位特征，现有报告不能作为模型准入依据。
- 国家队、俱乐部和不同联赛的数据覆盖不均；未匹配球队仍需通过受版本控制的别名表持续治理。
- 模型一致度只反映模型输出是否接近，不代表历史正确概率。
- SQLite 标准比赛仓库、球队别名、幂等导入和 JSON 迁移已实现；共享预测服务和可信 Walk-forward 回测尚未实施。

## 3. 优化目标

### 3.1 必须实现

- 相同数据、配置和模型产物必须得到相同预测结果。
- 重复启动不能重复训练、重复累计或改变 ELO。
- 未训练、输入缺失或不适用的模型不能进入融合。
- 线上预测与离线回测必须复用同一特征和模型调用路径。
- 每个线上模型必须能报告版本、训练时间、训练样本量和适用范围。
- 所有概率输出必须满足有限值、非负和归一化约束。
- 模型只有在严格时间外测试中通过准入门槛后才能进入融合。

### 3.2 暂不追求

- 不以维持“12 模型”数量为目标。
- 不以单场预测是否命中作为模型优劣依据。
- 不在回测可信之前调大模型复杂度。
- 不在业务边界明确之前合并足球、竞彩和彩票三套逻辑。

## 4. 总体实施顺序

| 阶段 | 主题 | 核心产物 | 进入下一阶段的条件 |
|---|---|---|---|
| 0 | 固定基线 | 测试框架、固定样本、当前行为报告 | 核心缺陷能由失败测试稳定复现 |
| 1 | 正确性修复 | ELO 重建、模型协议、权重迁移 | 重复运行稳定，融合只包含有效模型 |
| 2 | 数据治理 | 标准赛事实体、球队别名、数据质量报告 | 训练和预测数据来源可追踪、可去重 |
| 3 | 可信回测 | Walk-forward 回测、基线、分组指标 | 每个候选模型都有独立时间外结果 |
| 4 | 模型与融合 | 概率校准、模型准入、有效融合 | 融合在保留集上稳定优于简单基线 |
| 5 | 服务工程化 | 分层 API、后台任务、鉴权、可观测性 | 服务可安全部署并能定位数据/模型故障 |
| 6 | 产品治理 | 竞彩风控、彩票模块边界、用户提示 | 输出不夸大统计能力，操作风险可控 |

## 5. 阶段 0：建立固定基线

### 5.1 测试基础设施

- 新增开发依赖文件，例如 `requirements-dev.txt`，引入 `pytest` 和覆盖率工具。
- 建立 `tests/`，按 `unit/`、`integration/`、`fixtures/` 划分。
- 固定随机种子，覆盖蒙特卡洛、神经网络初始化和彩票号码生成。
- 测试不得依赖实时网络；抓取器测试使用保存并脱敏的 HTML/JSON 样本。
- 建立包含俱乐部、国家队、中立场、不同联赛、重复比赛和未知球队的最小比赛集。

### 5.2 首批回归测试

- 同一 ELO 文件连续初始化三次，评分应完全一致。
- 比赛按不同输入顺序载入时，应先按规范时间排序后产生相同评分。
- `knn` 旧权重能够迁移为 `knn_similar`。
- 未训练模型的 `available` 必须为 `false`，实际融合权重必须为 0。
- 任一模型返回 NaN、无穷值或非法概率时，融合层必须拒绝该输出。
- `/predict` 缺少球队、球队相同和输入赔率非法时返回稳定错误结构。
- 中立场比赛不能使用主场加成。

### 5.3 基线报告

只读诊断报告记录：

- 当前历史比赛数量及赛事分布。
- ELO 文件格式、球队数量和数据指纹。
- XGBoost、神经网络和 Stacking 的产物状态。
- 当前权重文件的键名、权重和未匹配项。

该报告仅用于确认行为变化，不作为模型质量结论。

### 5.4 退出条件

- 核心缺陷都有稳定失败测试。
- 测试可在无网络环境运行。
- `python -m compileall -q .` 和测试命令能够在本机一次通过或明确暴露已知失败。

## 6. 阶段 1：修复预测正确性

### 6.1 ELO 幂等化与数据迁移

- 将“从比赛重建 ELO”和“从新比赛增量更新 ELO”拆成两个明确入口。
- 完整重建必须从固定初始评分开始，并按开赛时间、稳定比赛 ID 排序。
- 保存文件增加 `schema_version`、`data_fingerprint`、`parameter_fingerprint`、`match_count` 和 `built_at`。
- 启动时只有数据指纹或参数版本变化才允许重建。
- 废弃并重建可能已重复累计的现有 ELO 产物，不直接沿用旧评分。
- 在稳定比赛 ID 建立前不自动去重；业务去重属于阶段 2。

验收：相同数据连续重建结果完全一致；输入顺序不影响结果；删除产物后可完整恢复相同评分。

### 6.2 统一模型协议

所有模型输出经协议适配器转换为统一结构：

```json
{
  "model_id": "poisson",
  "model_version": "1",
  "available": true,
  "status": "ready",
  "home_win": 0.42,
  "draw": 0.29,
  "away_win": 0.29,
  "data_quality": null,
  "warnings": []
}
```

协议要求：

- `model_id` 使用唯一规范名称。
- `available=false` 的模型不得进入蒙特卡洛和最终融合。
- 缺少球队数据时必须报告默认值使用情况。
- 融合前统一进行有限值、范围和概率和校验。
- 单个模型异常不得让整个请求返回伪造的正常概率。

### 6.3 权重迁移与融合修复

- 建立唯一模型 ID 清单，统一使用 `knn_similar`。
- 加载旧文件时执行 `knn -> knn_similar` 迁移；保存时只写新键。
- 对未知键、重复键、负权重和缺失键给出明确日志。
- 只对本次可用模型重新归一化权重。
- API 同时返回配置权重、模型可用状态和本次实际权重。
- 神经网络没有训练产物时退出融合，不再返回可用的固定先验。

### 6.4 结果表达修复

- 在完成概率校准前，将“置信度”改为“模型一致度”。
- 同时输出数据覆盖等级、使用默认值的模型数量和有效模型数量。
- 删除重复路由声明。
- 将裸 `except:` 替换为明确异常处理和结构化日志。

### 6.5 退出条件

- ELO 幂等测试通过。
- 旧权重迁移测试通过。
- 无效模型实际权重为 0。
- 所有线上预测概率通过统一校验。
- 固定输入连续运行结果在允许随机误差范围内一致。

## 7. 阶段 2：数据治理

### 7.1 标准比赛数据结构

每场比赛至少包含：

- 稳定 `match_id`。
- 标准主客队 ID 和原始球队名称。
- 赛事 ID、赛季、比赛阶段和赛事类型。
- UTC 开赛时间及原始时区信息。
- 中立场标记、比赛状态和最终比分。
- 数据来源、抓取时间和源站记录 ID。
- 数据质量状态和解析警告。

### 7.2 球队与赛事归一化

- 建立球队主表和别名表，区分中文名、英文名、简称和源站名称。
- 国家队与俱乐部使用不同命名空间，避免同名误合并。
- 赛事配置不能只依赖展示名称，应使用稳定赛事 ID。
- 无法映射的球队进入待处理列表，不静默创建多个近似球队。

### 7.3 去重与质量检查

- 优先按数据源 ID 去重；无源 ID 时使用赛事、球队和时间生成稳定指纹。
- 检查重复比赛、异常比分、未来赛果、时间倒序和缺失球队。
- 数据抓取失败与“当天确实没有比赛”必须区分。
- 保存数据质量报告，包括覆盖率、缺失率、别名命中率和默认值使用率。

### 7.4 存储策略

- 测试样本以小型 JSON 固定在仓库中。
- 运行时缓存和完整数据继续保持不入 Git。
- 逐步使用 SQLite 保存比赛、球队、数据源和模型运行记录。
- 数据导入和数据库结构变化使用显式迁移版本。

### 7.5 退出条件

- 固定测试集的球队别名命中率为 100%。
- 重复导入同一数据不增加比赛数量。
- 每条训练样本都能追踪到来源和抓取时间。
- 国家队、俱乐部和联赛可以独立查询与评估。

## 8. 阶段 3：重建可信回测

### 8.1 回测协议

- 比赛严格按时间排序。
- 采用滚动或扩展窗口 Walk-forward 验证。
- 每场预测只能使用该场开赛前可获得的数据。
- 特征生成必须调用与线上预测相同的服务，禁止离线占位特征。
- 训练、校准和最终保留测试集严格隔离。
- 同一场比赛的赔率只能使用开赛前对应时间点的数据。

### 8.2 基线模型

至少比较：

- 固定联赛主胜/平/客胜比例。
- 近期滚动联赛比例。
- 单一泊松模型。
- 单一 ELO 模型。
- 去水后的真实市场赔率；没有历史赔率时不得使用固定先验冒充市场基线。

### 8.3 评估指标

- Brier Score。
- Log Loss。
- Ranked Probability Score。
- Expected Calibration Error。
- 校准曲线。
- 按赛事、赛季、主客场、球队数据覆盖度分组的指标。
- 使用 bootstrap 或分块重采样提供不确定区间，避免把微小差异解释为确定提升。

命中率只能作为辅助展示，不能作为主要优化目标。

### 8.4 模型准入标准

模型进入线上融合前必须满足：

- 使用与线上相同的特征和预处理代码。
- 在时间外测试集完成评估。
- 在目标赛事上拥有足够有效样本。
- 至少稳定优于简单赛事比例基线。
- 相比现有线上融合没有显著恶化 Log Loss 或校准误差。
- 能提供训练数据范围、版本、样本量和评估报告。

无法击败基线的模型可以保留作研究，但默认权重为 0。

### 8.5 退出条件

- 废弃当前不可比的校准报告，并生成版本化新报告。
- 所有候选模型都有相同协议下的时间外结果。
- 报告能够复现，并记录代码提交、数据指纹和参数版本。

## 9. 阶段 4：模型与融合优化

### 9.1 优先顺序

先建立少量可靠模型：

1. 泊松或 Dixon-Coles。
2. ELO。
3. 近期状态模型。
4. 有真实历史赔率时的市场模型。

再评估：

5. 贝叶斯层次模型。
6. KNN。
7. XGBoost。
8. 神经网络。
9. Stacking。

蒙特卡洛属于采样和结果推演方法，不应因为重复采样其他模型结果就自动视为独立信息源。

### 9.2 特征一致性

- 训练和线上预测共用一个 `FeatureBuilder`。
- 训练产物保存特征名、顺序和预处理参数。
- 加载模型时校验特征版本，不兼容时拒绝预测。
- `massey_diff` 等尚未真实填充的特征不得以固定零值长期参与训练。
- 缺失值处理必须在训练和推理中一致。

### 9.3 概率校准与融合

- 对单模型概率使用独立校准集进行 isotonic、Platt 或多分类校准。
- 分析模型输出相关性，避免高度相关模型重复放大相同信息。
- BMA 若继续使用，应准确描述其权重算法；当前基于 Brier 的启发式加权不应宣称为严格贝叶斯后验。
- Stacking 只能使用各基础模型的 out-of-fold 预测训练。
- 对国家队、俱乐部和主要联赛分别评估是否需要不同权重。

### 9.4 真实可信度

在概率校准完成后，可信度应综合：

- 历史校准误差。
- 目标球队有效样本量。
- 数据新鲜度和球队映射质量。
- 可用模型数量。
- 输入是否超出训练分布。

可信度表示概率可靠程度，不表示“本场一定命中”。

### 9.5 退出条件

- 线上融合只由通过准入的模型组成。
- 消融实验能够说明每个模型的实际贡献。
- 新融合在最终保留集上稳定优于简单基线和最佳单模型，或明确证明选择单模型更合理。

## 10. 阶段 5：服务工程化

### 10.1 代码分层

- 将 Flask 路由拆分为预测、历史、竞彩、校准、数据同步和彩票 Blueprint。
- 路由只负责输入验证和响应转换。
- 模型加载、预测编排、数据访问和后台任务分别放入服务层。
- 使用应用工厂创建 Flask 应用，便于测试和不同环境配置。

### 10.2 后台任务

- 数据刷新、FIFA 同步和校准使用受控后台任务。
- 同一类型任务设置互斥锁，禁止重复启动。
- 保存任务 ID、状态、开始时间、结束时间和错误摘要。
- 服务重启后能够识别中断任务，而不是永远显示运行中。

### 10.3 API 与安全

- 会写入状态的接口改为 POST。
- 局域网或公网部署时，对刷新、同步和校准接口增加鉴权。
- 对请求参数、赔率范围、球队名称和分页大小进行结构化校验。
- 不向客户端直接返回内部异常堆栈。
- 增加请求日志、模型版本和预测运行 ID。

### 10.4 部署

- 开发环境可继续使用 Flask 内置服务器。
- 部署环境使用 Waitress 或其他 WSGI 服务。
- 主机、端口、日志级别、数据库和缓存路径通过环境配置提供。
- 健康检查区分 Web 可用、数据可用和模型可用。

### 10.5 退出条件

- API 测试不依赖全局模型副作用。
- 后台任务不会重复执行。
- 写操作具备明确权限边界。
- 能从日志定位某次预测使用的数据和模型版本。

## 11. 阶段 6：竞彩与彩票产品治理

### 11.1 竞彩足球

- 明确主页 12 模型流程与 `JczqEngine` 独立流程的关系。
- 优先考虑让竞彩分析复用统一预测服务，避免维护两套互相矛盾的概率。
- EV 必须使用真实赔率时间点，并记录水位和更新时间。
- 资金建议设置单场、单日和组合上限；凯利公式只能使用折扣比例。
- 回测同时报告收益、最大回撤、样本量和赔率可成交假设。

### 11.2 彩票模块

- 彩票结果本质上是独立随机事件，历史冷热号不能证明能提高未来中奖概率。
- 页面与文档应使用“统计分析”而非暗示确定性的“智能预测”。
- 明确展示随机性说明和理性参与提示。
- 彩票代码、测试、路由和配置继续与足球预测隔离。

## 12. 测试体系

### 12.1 单元测试

- 概率计算、ELO 更新、球队别名、特征构建、权重迁移和融合校验。

### 12.2 契约测试

- 所有模型必须满足统一返回协议。
- 所有 API 错误必须满足统一错误结构。

### 12.3 集成测试

- 固定数据库到 `/predict` 的完整预测流程。
- 校准报告生成和模型产物加载。
- 数据重复导入和增量更新。

### 12.4 数据测试

- 唯一键、时间、比分范围、球队映射、赛事类型和数据来源。

### 12.5 持续集成

每次 Pull Request 至少运行：

```bash
python -m compileall -q .
pytest -q
```

涉及模型或数据逻辑时，再运行固定小型回测。完整历史回测可以作为定时任务，不应阻塞每次小改动。

## 13. Git 交付规范

- 每个阶段使用独立分支，分支名使用 ASCII，例如 `codex/elo-idempotency`。
- Git 提交信息使用中文，并保证一个提交只表达一个可回滚的目的。
- 数据迁移、行为修改和格式化不混在同一个提交中。
- 提交模型逻辑时，同时提交对应测试和必要文档。
- 不提交运行时数据、缓存、个人 IDE 配置和本地模型产物。

推荐提交示例：

```text
test: 增加 ELO 重复初始化回归测试
fix: 重建 ELO 并避免重复处理历史比赛
fix: 迁移 KNN 权重键并过滤不可用模型
refactor: 统一模型预测结果协议
docs: 补充模型准入与回测规范
```

## 15. 完成定义

一项优化只有同时满足以下条件才算完成：

- 有明确的问题描述和验收标准。
- 有能在修复前失败、修复后通过的测试，或说明为何无法自动测试。
- 不依赖开发者本机未提交的隐式数据或模型文件。
- 日志和 API 能说明实际使用的数据与模型状态。
- 已执行编译检查、定向测试和必要回测。
- 文档、README 和项目协作约定与代码保持一致。
- Git 提交内容单一、说明为中文且可以安全回滚。
